Temple CRM — Security Hardening

Implementation Plan

Scope: Audit Trail, Account Lockout, HTTP Security Headers Live URL: https://temple-crm-web.onrender.com Document Version: 1.0

Overview

Three security features were identified as high-value additions, each mapped directly to a CompTIA security domain: a comprehensive audit trail of sensitive actions, account lockout to blunt password guessing, and standard HTTP security headers. All three are implemented in the codebase; the summary below shows what each does, why it matters for an application handling donation records and member PII, and how it was built.

1. Comprehensive Security Audit Trail

Implemented
Immutable record of every sensitive action

What it does: A new SecurityAuditLog table captures who did what, when, and to what — every login (success and failure), logout, account lockout, record deletion, role change, and other admin action (user creation, spreadsheet import, fact sheet upload, payment settings change).

Why it matters: If a donation record is ever deleted or a role is changed and someone asks "who did that, and when?" — the audit trail is the answer, not a guess. This is exactly the kind of control CompTIA's logging & monitoring domain calls for, and it's the first thing a client asks about when handling donor PII.

  • New model: website/models.py — SecurityAuditLog
  • New helper: website/audit.py — log_event(...), fails safe (never blocks the action it's logging)
  • New page: /admin/security-log (Super Admin only) — filterable by event type, latest 300 shown

2. Account Lockout & Brute-Force Protection

Implemented
Five strikes, fifteen-minute lock — stored in the database

What it does: After 5 failed login attempts on one account (wrong password, or wrong Super Admin PIN), that account is locked for 15 minutes. The counter and lock time live on the User row itself, so a server restart doesn't reset an attacker's progress or accidentally unlock someone mid-attack.

Why it matters: The login form had zero rate limiting before this — an attacker could guess passwords indefinitely. This directly addresses credential-stuffing/brute-force, a named attack category in CompTIA's authentication material, and every failed/locked attempt also lands in the audit trail above.

  • Schema: failed_login_attempts, locked_until added to User
  • Logic: website/auth.py login() — locks after 5 failures, resets on success
  • UX: remaining-attempts warning shown before lockout kicks in

3. HTTP Security Headers

Implemented, gated
Flask-Talisman: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, HSTS

What it does: Adds the standard set of browser-enforced protections against clickjacking, MIME-sniffing, and content injection. The Content-Security-Policy is scoped to explicitly allow the app's existing inline scripts/styles and the exact CDN origins it already depends on (Bootstrap, jQuery, Google Fonts) — real headers today, with zero visual regressions, instead of a much larger rewrite to eliminate inline code.

Why it matters: These headers are checkable and visual — running the live site through securityheaders.com or Mozilla Observatory produces a concrete, screenshot-able grade for a client, with very little implementation risk.

  • Dependency: flask-talisman, wired in website/__init__.py create_app()
  • ProxyFix added so the app correctly recognizes HTTPS behind Render's edge proxy
  • FORCE_HTTPS env var defaults to off everywhere — headers are active, but nothing forces an HTTPS redirect yet
Rollout sequencing — do not skip

The in-person, multi-device test (local network + Render fallback) was still upcoming when this was built. Forcing HTTPS redirects prematurely would break local http://<lan-ip>:5050 access during that test. FORCE_HTTPS must stay unset until that test is confirmed complete — only then should it be added to render.yaml's envVars and pushed, as a separate, deliberate step.
